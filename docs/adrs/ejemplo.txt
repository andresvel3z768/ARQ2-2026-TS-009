# ADR 001: API Gateway as an only entry point (Kong)

- Status: Proposed

- Context: Hundreds of agencies have bots that query the same flight every second, and these requests currently go directly to the airlines, which impose penalties for exceeding their rate limits. Additionally, each service reimplements authentication, and there is no idempotency validation at the point of purchase entry. A single entry point is needed to authenticate requests, rate-limit traffic per agency, validate the Idempotency-Key, and generate the X-Correlation-ID.

- Alternatives: (1) Kong Gateway (OSS) with plugins; (2) Apache APISIX; (3) Gateway propio en Node.js/Express; (4) Nginx con Lua.

- Decision:Kong Gateway (DB-less mode, using declarative configuration in kong.yml) with the jwt/key-auth, rate-limiting (with a redis policy), and correlation-id plugins, along with a lightweight idempotency plugin backed by Redis.

- Trade-offs:
- Pros: Per-agency rate limiting without writing custom code; centralized authentication; version-controlled configuration in the repository; simple deployment using Docker Compose; abusive requests are rejected (429) before reaching any microservice.
- Cons: It is a single point of failure and adds approximately 1–3 ms of latency. Mitigation: Use stateless DB-less replicas and health checks; the state is stored in Redis. The idempotency plugin requires a small Lua component.


# ADR 002: RabbitMQ as the Messaging Broker for the Purchase Saga

- Status: Proposed

- Context: The purchase workflow involves inventory, agency balance, and a slow and unstable external airline. It must tolerate partial failures, retries, and the delivery of commands and responses between services without synchronous coupling. Service-specific queues, routing by event type, dead-letter handling, and delivery acknowledgments are required.

- Alternatives: (1) RabbitMQ; (2) Apache Kafka; (3) Redis Streams; (4) Synchronous HTTP between services.

- Decision: Use RabbitMQ with a `topic` exchange (`aerobooking.events`), durable consumer-specific queues, *publisher confirms*, manual *consumer acknowledgments (acks)*, and a DLX for failed messages.

- Trade-offs:

- Pros: Flexible routing through routing keys (commands and events on the same bus); native DLQ and TTL support for retries; low message latency; simple operation in a single container with a management console.

- Cons: Lower raw throughput than Kafka and no historical *replay*. **Mitigation:** Historical records are handled by the Audit Service (append-only), and purchase volume is moderate. Delivery is *at-least-once*, so all consumers implement an idempotent inbox.

# ADR 003: Redis for Fare Caching, Single-Flight, and Rate Limiting Toward Airlines

- Status: Proposed

- Context: Agencies repeat the same search every second, and every request reaches the airline, which penalizes requests that exceed its rate limit. Fares are valid for a limited period, so they can be served from memory during that time. Additionally, even with caching, 100 simultaneous searches during a *cache miss* could generate 100 calls to the airline (*cache stampede*).

- Alternatives: (1) Redis (caching + locks + counters); (2) Memcached; (3) In-memory caching on each instance (Caffeine/node-cache); (4) HTTP CDN/proxy caching.

- Decision: Use Redis with:
- (a) Keys in the format `fare:{airline}:{origin}:{dest}:{date}:{cabin}:{pax}` and a per-airline TTL (60 seconds by default), plus a 15-second *stale-while-revalidate* window.
- (b) *Single-flight*: `SET lock:fare:{key} NX PX 5000` so that only one request queries the airline while the others wait or receive the *stale* value.
- (c) A global *token bucket* per airline (Lua script) in the Airline Connector to ensure the airline's contractual rate limit is never exceeded.
- (d) A circuit breaker that serves *stale* cached data if the airline fails.

- Trade-offs:

- Pros: Sub-millisecond reads; the number of calls to the airline depends on the TTL rather than the number of bots; explicit protection against penalties; the same Redis instance supports locks and idempotency, reducing the number of components.

- Cons: A fare may be outdated for up to the TTL, so the purchase process **revalidates the price** with the airline and fails with `PRICE_CHANGED` if it has changed. Redis is a single point of failure, mitigated through AOF persistence and, in the future, Sentinel/Cluster. If Redis goes down, the Gateway returns 503 instead of forwarding traffic to the airlines.

# ADR 004: Distributed Seat Locking with Redis and Fencing Tokens

- Status: Proposed

- Context: Two agencies may attempt to purchase seat 12A on the same flight at almost the same time. Currently, both receive a local success response, and only afterward does the airline reject the second request. Inventory must be reserved exclusively for a short period immediately before checkout, preventing a slow or paused process (due to garbage collection or network delays) from continuing to act with an expired lock.

- Alternatives: (1) Redis lock (`SET key token NX PX ttl`) with a fencing token; (2) Redlock across multiple Redis nodes; (3) `SELECT ... FOR UPDATE` in PostgreSQL; (4) ZooKeeper/etcd.

- Decision: The Inventory Service acquires `seatlock:{flightId}:{seat}` using `SET NX PX 120000` (with a unique token as the value) and increments a counter using `INCR fence:{flightId}:{seat}` to generate a *fencing token* that is passed along with subsequent commands. The lock is released through a Lua script that verifies the token. The final state (`SOLD`) is persisted in `inventory_db`.

- Trade-offs:

- Pros: Acquisition in microseconds without blocking SQL connections; TTL prevents permanent locks if a service crashes; the fencing token allows messages from an expired lock holder to be discarded; no open transactions are maintained while waiting for the airline.

- Cons: A lock on a single Redis instance does not provide an absolute guarantee during network partitions or failover. **Mitigation:** The lock reduces contention but is not the source of truth. The airline is the authoritative source, so the saga treats its rejection as a normal case and triggers automatic compensation (ADR 005). Redlock is rejected due to its complexity and the debate surrounding its correctness.
